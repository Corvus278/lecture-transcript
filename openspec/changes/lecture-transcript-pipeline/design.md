## Context

Мотивация — см. `proposal.md` → Why. Требования — см. `specs/`.

Эталонная запись, на которой валидируются решения:

```
wr_20260909_1150.mp4 — 1:31:22, 830 MB
  video: h264 1920x1080
  audio: aac 48 kHz, MONO, одна дорожка
```

Что видно на кадрах: вебинар по математике, слайды демонстрируются в левой/верхней части кадра, вокруг — сетка из 20+ тайлов участников с подписанными ФИО. Демонстрация включается и выключается по ходу пары; при выключении тайлы перестраиваются на весь кадр. Лектор дописывает поверх слайдов маркером. Активный говорящий подсвечивается рамкой тайла.

Ограничения окружения:

- WSL2 + Docker на Windows, одна GPU RTX 4060 8 GB
- всё локально: в кадре ФИО студентов, наружу ничего не уходит
- одна аудиодорожка, моно-микс — поканального разделения говорящих нет в принципе

## Goals / Non-Goals

**Goals:**

- Один прогон `mp4` → `transcript.md` за время, сопоставимое с длительностью перерыва между парами
- Сменные бэкенды ASR и OCR за едиными контрактами — модель выбирается под предмет и язык лекции
- Устойчивость к смене платформы вебинара: никаких хардкодов под оформление конкретного шаблона
- Пиковый расход VRAM заведомо ниже 8 GB

**Non-Goals:**

- Разделение речи по спикерам — отдельный будущий change (детект рамки активного спикера + OCR ФИО)
- Генерация конспекта LLM — пайплайн заканчивается на `transcript.md`
- Реальное время и стриминг — обработка только пост-фактум
- Распознавание рукописного ввода

## Decisions

### D1. Видеотрек обязателен, а не опционален

Аудио-only решение отвергнуто. По эталонной записи значимая часть содержания (формулы, нотация) существует только на слайдах: произнесённое «корень из икс квадрат минус икс равно минус пять» не восстанавливается в `√(x²−x) = −5` никакой обработкой текста. Для математических предметов расшифровка без слайдов бесполезна как основа конспекта.

Альтернатива — аудио-only MVP с добавлением слайдов позже — отклонена: формат `transcript.md` и разбиение на секции строятся вокруг слайдов, так что добавление видео позже означало бы переписывание сборки, а не дополнение.

### D2. Порядок веток: видео → глоссарий → аудио

Ветки не параллельны. Слайды обрабатываются первыми, потому что дают глоссарий терминов лекции, а он подаётся в ASR как hotwords / `initial_prompt`:

```
[1] кадры -> область слайда -> дедуп -> OCR -> глоссарий
                                                  |
[2] аудио -> VAD -> ASR(глоссарий) -> пунктуация -+
                       |
[3] merge по времени -> transcript.md
```

ASR ошибается в первую очередь на терминах и именах собственных — то есть ровно на том, что важно для конспекта. Глоссарий из слайдов этой конкретной лекции срезает эти ошибки и достаётся бесплатно, как побочный продукт ветки слайдов.

### D3. Область демонстрации — по временно́й дисперсии, не по цвету рамки

У эталонной платформы слайд обрамлён характерной рамкой, и соблазн детектить по её цвету велик. Отвергнуто: сломается на любом другом шаблоне и на другой платформе.

Вместо этого — свойство, общее для всех платформ видеосвязи: **область демонстрации статична во времени, а видеотайлы — нет**.

```
сэмплируем ~100 кадров по всей записи, считаем per-pixel variance:

  вебки участников:  высокая дисперсия (люди двигаются), тёмный фон
  область слайда:    низкая дисперсия, высокая яркость (слайды светлые)

область слайда = крупнейший связный прямоугольник,
                 светлый И низкодисперсный
```

Тот же признак бесплатно решает вторую задачу — детект «демонстрация выключена»: такого региона просто нет.

Раскладка меняется в течение записи, поэтому дисперсия считается не по всей записи разом, а по скользящим окнам; область слайда фиксируется на интервал стабильной раскладки.

### D4. Дедупликация: representative = последний кадр, не первый

Лектор дописывает поверх слайда. Значит perceptual hash одного логического слайда плывёт постепенно:

```
t:  40:00      41:30      44:10      47:00   ->  48:00
    "Пример 2" +начало   +преобраз. +ответ        новый слайд
    hash: A      A'         A''        A'''       B
    |__________ один логический слайд __________|
                                        ^
                                  БРАТЬ ЭТОТ КАДР
```

Наивный scene-detect здесь ошибается дважды: разбивает слайд на 5–10 «разных» и берёт первый кадр каждого — то есть пустую заготовку без решения.

Решение: группировка по hamming distance с порогом (постепенные дописывания дают малую дистанцию, смена слайда — большую), representative — последний кадр группы, содержащий наиболее полное состояние.

Возврат к ранее показанному слайду намеренно порождает отдельную группу: у него свой временно́й интервал и своя речь.

### D5. OCR: гибрид спец-моделей, рукописное не распознаём

Содержимое слайда делится на три категории с принципиально разной распознаваемостью:

```
+----------------------------------------------------+
|  Пример 2.  v(x^2 - x) = -5                        |
|  ^^^^^^^^^  ^^^^^^^^^^^^^^^                        |
|  [1] печ.   [2] печ. формула                       |
|      текст                                         |
|                 (/)  <-- [3] рукописная пометка    |
+----------------------------------------------------+

[1] PaddleOCR ru  -> ~99%. Крупный шрифт на белом фоне — идеальные условия
[2] pix2tex       -> ~85%. Печатные формулы в LaTeX. Модель ~100 MB
[3] не берётся локально ни OCR, ни pix2tex, ни VLM в пределах 8 GB
```

Категория [3] решается **не моделью, а ссылкой**: кроп слайда сохраняется как PNG, транскрипт ссылается на него.

```markdown
> **Пример 2.** $\sqrt{x^2-x} = -5$
> ![слайд 12](slides/012.png)
```

Это осознанный отказ от полноты распознавания. Обоснование: конспект пишет человек, и изображение слайда под рукой полезнее, чем галлюцинация модели на месте рукописной записи. Попытка распознать всё дала бы худший результат, чем честный пропуск.

Роутинг внутри бэкенда: PaddleOCR отдаёт боксы строк с confidence; строки с математическими символами или низкой уверенностью уходят в pix2tex, остальное берётся как текст.

Альтернативный бэкенд за тем же контрактом — Qwen2.5-VL (4bit), один проход на слайд сразу в Markdown+LaTeX: меньше кода, но ~6 GB VRAM и склонность галлюцинировать в формулах. Держим как опцию, по умолчанию не используем.

### D6. ASR: GigaAM-v2 по умолчанию, Whisper для смешанной речи

| | GigaAM-v2 | Whisper large-v3 |
|---|---|---|
| русский | WER заметно ниже | базовый уровень |
| латиница в речи | ломается | распознаёт |
| размер | ~240M (~1 GB fp16) | ~1.5B (~4.7 GB fp16) |
| пунктуация | нет (CTC/RNNT) | есть |
| лицензия | MIT | MIT |

GigaAM-v2 — по умолчанию для русских лекций. Whisper large-v3 — когда в лекции много англоязычных терминов и важно сохранить латиницу.

Следствие из таблицы: пунктуация не может быть частью ASR-бэкенда, потому что один бэкенд её даёт, а другой нет. Поэтому восстановление пунктуации и регистра — отдельная стадия, которая включается только для бэкендов, объявивших, что своей пунктуации у них нет.

### D7. Стадии последовательные, модели выгружаются

```
СТАДИЯ            МОДЕЛЬ                    VRAM      ВРЕМЯ (91 мин)
-----------------------------------------------------------------
1 декод + кроп    ffmpeg nvdec, 1 fps         -        ~2 мин
2 дедуп слайдов   phash (CPU)                 -        <1 мин
3 OCR слайдов     PaddleOCR + pix2tex      ~0.6 GB     4-8 мин
4 VAD             silero                   ~0.05 GB    <1 мин
5 ASR             GigaAM-v2 RNNT           ~1.0 GB     3-5 мин
6 пунктуация      модель для ru            ~0.7 GB     ~1 мин
7 merge           -                           -        сек
-----------------------------------------------------------------
                                            ИТОГО      ~15 мин
```

Пиковый расход ~1.5 GB при бюджете 8 GB. Запас нужен не «на всякий случай», а под альтернативные бэкенды: Whisper large-v3 (4.7 GB) вместо GigaAM и Qwen2.5-VL (6 GB) вместо PaddleOCR+pix2tex тоже помещаются — но только по одному за стадию, поэтому выгрузка модели между стадиями обязательна, а не опциональна.

Вывод по железу: **8 GB на этом плане не жмут**. Узкое место — точность OCR формул, а не VRAM.

### D8. Кэш промежуточных артефактов по этапам

Прогон занимает ~15 минут, а итерации по формату транскрипта и правилам чистки речи будут частыми. Декодировать 830 MB и заново гонять ASR ради изменения шаблона вывода — недопустимо долгий цикл обратной связи.

Кэш ключуется входным файлом и параметрами этапа: смена частоты выборки кадров инвалидирует кадры, смена ASR-бэкенда — распознавание речи, смена шаблона вывода — только сборку.

## Risks / Trade-offs

- **Точность pix2tex на формулах ~85%** → ссылка на PNG слайда рядом с каждой формулой: ошибка распознавания видна и исправима глазом, а не молча уносится в конспект.
- **Детект области демонстрации по дисперсии может ошибиться** на записи со статичной заставкой вместо вебок или с очень тёмными слайдами → валидация на эталонной записи, при неуверенном детекте — явная диагностика и возможность задать область вручную.
- **Дописывание маркером против порога hamming distance** → порог подбирается на эталонной записи; ошибка в сторону дробления безопаснее ошибки в сторону склейки: лишний слайд заметен, потерянное решение — нет.
- **GigaAM без пунктуации** → отдельная стадия восстановления; риск в том, что она может сдвинуть привязку слов к таймкодам, поэтому таймкоды берутся из ASR и не пересчитываются после расстановки пунктуации.
- **Вопросы студентов через дешёвые микрофоны в моно-миксе** → распознаются заведомо хуже речи лектора. В этой версии они попадают в общий поток; помечать их отдельно станет возможно только после ветки со спикерами.
- **Чистка филлеров может удалить содержательное** → правила консервативные, чистятся только явные заполнители и оборванные самоповторы; сомнительное остаётся.
- **Смена шаблона вебинара платформой** → сломает детект области. Дисперсионный подход снижает риск по сравнению с привязкой к цвету рамки, но не устраняет.

## Open Questions

- Конкретное значение допуска на границах секций (D2 в `transcript-assembly`) — подбирается на эталонной записи, на архитектуру не влияет.
- Порог confidence, при котором фрагмент OCR помечается неуверенным — подбирается эмпирически.
- Нужен ли батч-режим для потока пар каждую неделю — зависит от того, станет ли инструмент регулярным; на структуру пайплайна не влияет, добавляется поверх.
